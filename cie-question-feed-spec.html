Internal build reference

CIE Question Feed — what to build

This page is for the developer. The top half is the written spec. Below it is a working front-end mockup (real MathJax rendering, real parsing of the LaTeX constructs we need) that you can literally open in a browser, paste a question into, and post to a mock feed — treat it as the reference implementation for the composer + renderer, not just a wireframe.

1 · What we're building

A Facebook-style feed where each post = one exam question. The author pastes LaTeX copied straight out of a CIE source file (no \documentclass, no preamble, no \begin{document}) into a text box, optionally attaches images and a mark scheme / sample answer, previews it rendered, and publishes. Other users then see it rendered in the feed, same as any other post.

Core technical challenge: MathJax/KaTeX only render math — the stuff between $…$ or $$…$$. They do not understand \begin{enumerate}, \begin{tabular}, \textbf{}, or \includegraphics{} — those are text-mode LaTeX, not math-mode. We need a small pre-processing step that converts that text-mode LaTeX into HTML before MathJax ever sees the string, and leaves the math delimiters untouched so MathJax can do its part after. The mockup below implements exactly this pre-processor — see parseLatexFragment() in the page source.
2 · Rendering pipeline (order matters)
  1. Sanitize / strip wrapper noise. If someone pastes a full document by accident, regex out \documentclass{...}, \usepackage{...}, \begin{document}, \end{document} before anything else runs.
  2. Protect math regions. Extract every $...$ and $$...$$ span and stash it (e.g. replace with a placeholder token) so the next step's HTML conversion can't mangle backslashes or braces inside actual math.
  3. Convert text-mode LaTeX → HTML on what's left:
    • \begin{enumerate}…\end{enumerate} + \item → <ol><li> (CIE papers nest these for (a), (i), (ii) — support nested enumerate with different counters, e.g. enumerate[label=(\alph*)])
    • \begin{center}…\end{center} → <div style="text-align:center">
    • \begin{tabular}{...}…\end{tabular} → <table>, splitting rows on \\ and cells on &, treating \hline as a row border
    • \textbf{} / \textit{} / \underline{} → <b> / <i> / <u>
    • \includegraphics[options]{filename} → <img src="…">, see mapping strategy below
  4. Restore the math placeholders back into the HTML, untouched.
  5. Hand the resulting HTML to MathJax (MathJax.typesetPromise()) to render the $…$ / $$…$$ spans in place.
Don't reach for a full LaTeX-to-HTML compiler (e.g. trying to run real pandoc/LaTeX server-side) unless CIE content turns out to use far more commands than the ones above — it's slower, harder to sandbox safely, and this is a small, fairly fixed vocabulary of commands. Start with the targeted pre-processor; extend the regex/rule set as new commands show up in real pasted content.
3 · Handling \includegraphics

\includegraphics{diagram1.eps} refers to a file on the original LaTeX author's disk — we don't have that file. Two ways to bridge this, pick one:

Option A — filename matching simplest, error-prone

When the user uploads images alongside the text, match each uploaded filename against the \includegraphics{...} reference by name (stripping the extension, since CIE source often says .eps/.pdf but the uploaded file is a .png/.jpg). Fragile if names don't line up exactly.

Option B — ordered placeholders recommended

Ignore the filename entirely. Replace the 1st \includegraphics in the text with the 1st uploaded image, the 2nd with the 2nd, and so on, in document order. This is what the mockup below does. Simpler and matches how question-setters actually paste content (images in the same order they appear in the question).

Either way: if there are more \includegraphics tags than uploaded images, render a visible "missing image" placeholder box rather than silently dropping it — the poster needs to notice and fix it before publishing.
4 · Data model
Field Type Notes
question_latex text Raw pasted LaTeX for the question body, stored as-is (render on read, never pre-convert to HTML at write time — keeps the source editable and future-proofs against renderer changes)
mark_scheme_latex text, nullable Same raw-LaTeX-in, render-on-read approach
sample_answer_latex text, nullable Same
images array of file refs Uploaded files in the order they should map to \includegraphics occurrences (Option B above)
metadata object Subject, paper/session code, question number, marks — whatever the site needs for filtering/search; not part of the rendering pipeline itself
Store raw LaTeX, not pre-rendered HTML. Rendering is cheap and client-side; storing raw source means you can fix a parsing bug later and every old post benefits, instead of being frozen with whatever the converter produced at post-time.
5 · Admin / composer UI

Built and working in the mockup below:

  • Tabbed text areas for Question / Mark scheme / Sample answer (mark scheme and sample answer optional, collapsed by default on the published post — see the feed cards below)
  • Image upload with filename chips showing upload order (since order = the includegraphics mapping)
  • Toggle between side-by-side and tabbed preview layouts — side-by-side is nicer on desktop, tabbed is what you'd fall back to on mobile widths
  • Live preview re-renders on every keystroke (debounce this in production — the mockup re-renders on a short timeout, don't call MathJax on every single keypress with no debounce, it'll stutter on longer questions)
